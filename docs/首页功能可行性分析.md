# 首页功能可行性分析

> 分析日期：2026-05-07
> 分析范围：`docs/首页设计.md` 中三大功能模块
> 基准架构：FastAPI + React 18 + PostgreSQL 16 + feedparser

---

## 一、顶部卡片（日环比 + Sparkline）

### 技术可行性：✅ 高

本质是**计数聚合 + 时间序列可视化**，技术上没有障碍。

### 数据现状

| 指标 | 源表 | 当前支持度 |
|------|------|-----------|
| 新增 AI 产品数 | `ai_tools.created_at` | ✅ 字段已有，直接 COUNT |
| 值得拆解 | — | ❌ 缺少"拆解"标记机制 |
| 重点赛道 | `ai_product_types` | ✅ 字段已有，COUNT is_active |
| 异动提醒 | — | ❌ 缺少异常事件表 |

### 关键缺口：无时间序列基础设施

Sparkline（`▁▂▃▂▅▃▆▇`）和日环比都需要"今天的值 vs 昨天的值"，这要求记录每日快照。当前表结构只存当前状态，没有历史趋势记录。

### 建议方案

**新增一张轻量事实表（每日定时快照）：**

```sql
CREATE TABLE daily_metrics (
    id          SERIAL PRIMARY KEY,
    metric_date DATE NOT NULL,
    metric_name VARCHAR(50) NOT NULL,     -- 'new_tools', 'featured', 'active_tracks', 'alerts'
    metric_value INTEGER NOT NULL,
    created_at  TIMESTAMPTZ DEFAULT now(),
    UNIQUE(metric_date, metric_name)
);
```

- 后端新增 `GET /api/dashboard/summary` 端点，返回当日各指标值 + 最近 7 天值数组
- 前端用 Tailwind 渲染 4 列卡片网格，Sparkline 用 20px 高的 SVG 或 CSS 宽度条
- 每日快照通过 systemd timer 触发 Python 脚本，或由后端首次请求时惰性计算

### 实现复杂度：⭐⭐（低）

- 后端：1 个新 model + 1 个新 router + 1 个定时脚本（约 80 行）
- 前端：1 个新 `DashboardCards` 组件（约 100 行）
- 数据：建 1 张表
- 预估人天：**1-2 天**

## 二、赛道热力图（5 维度评分）

### 技术可行性：⚠️ 中等偏复杂

架构上可行，但**数据采集和评分体系是全新的业务域**，远超现有 CRUD 的复杂度。

赛道（track）在现有设计中明确作为 Phase 5 待建项标记在 DATABASE.md：
> "不设 tracks 赛道表——赛道偏市场分析，对用户找工具边界模糊，后期补"

当前只有 `ai_product_types`（工具分类），它和"赛道"是不同概念——产品类型是静态标签（"AI 视频工具"），赛道是动态市场分析单元（"AI 视频赛道"包含技术演进、竞争格局、风险等）。

### 5 维度评分的数据缺口

| 维度 | 所需数据 | 数据源 | 当前状态 |
|------|---------|--------|---------|
| 能力突破密度 | capability_releases | 官网/更新日志/评测 | ❌ 无表，需新采集 |
| 场景刚需强度 | target_user, task_frequency, pain_point | 行业分析 | ❌ 无表，需定性评估 |
| 工作流嵌入度 | api_available, integration_count | 产品文档 | ❌ 无表，需逐个审计 |
| 产品形态成熟度 | ui_pattern, pricing_model | 产品体验 | ❌ 无表，需逐个审计 |
| 技术依赖度 | model_dependency, platform_dependency | 技术架构分析 | ❌ 无表，需逐个审计 |

评分方案（文档提到"确定好字段，模型来设计权重和算法"）是**半自动化**的：
1. 人工/爬虫收集原始信号数据
2. LLM 按权重模板评分
3. 结果持久化到数据库

### 建议方案（分层建设，一期先上骨架）

**第一层 — 基础表：**

```sql
-- 赛道主表
CREATE TABLE market_tracks (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    slug        VARCHAR(120) UNIQUE NOT NULL,
    description TEXT,
    sort_order  INTEGER DEFAULT 0,
    is_active   BOOLEAN DEFAULT TRUE
);

-- 维度定义表
CREATE TABLE track_score_dimensions (
    id          SERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    slug        VARCHAR(120) UNIQUE,
    weight      FLOAT DEFAULT 1.0,
    description TEXT
);

-- 评分结果表（每赛道每维度每期一条）
CREATE TABLE track_scores (
    id           SERIAL PRIMARY KEY,
    track_id     INTEGER REFERENCES market_tracks(id),
    dimension_id INTEGER REFERENCES track_score_dimensions(id),
    score        FLOAT NOT NULL CHECK (score >= 0 AND score <= 100),
    period       DATE NOT NULL,
    source_note  TEXT,
    created_at   TIMESTAMPTZ DEFAULT now(),
    UNIQUE(track_id, dimension_id, period)
);
```

**第二层 — 后端 API：**
- `GET /api/tracks` — 赛道列表
- `GET /api/tracks/{id}/scores` — 某赛道最新评分
- `GET /api/tracks/heatmap` — 全部赛道热力图数据

**第三层 — 评分工具：**
- Python 脚本接收原始信号 → 调用 LLM → 写入 `track_scores`
- 不依赖 Web 进程，可由定时任务触发

### 落地难点

1. **数据采集是最大瓶颈** — 5 个维度的信号数据需持续从多渠道获取，纯爬虫很难覆盖全
2. **评分标准的稳定性** — 权重和算法在早期会频繁调整
3. **赛道与产品类型的映射** — 现有 `ai_product_types` 和新 `market_tracks` 需要关联

### 实现复杂度：⭐⭐⭐⭐（高）

一期建表和 API 骨架约 200 行后端代码 + 1 个新前端组件。真正复杂度在数据管道和评分体系。
预估人天：**3-5 天（一期骨架）**

## 三、今日值得拆解（产品卡片 + 系数评分）

### 技术可行性：✅ 高

本质是 **CRUD + 评分字段扩展**，和现有架构完全兼容。

### 数据现状

| 所需字段 | 当前状态 | 方案 |
|---------|---------|------|
| 一句话定位 | ✅ `short_description` 已存在 | 直接复用 |
| 赛道标签 | ✅ `product_type` / `use_case` 关联 | 直接复用 |
| 核心看点 | ⚠️ `overview` 字段 | 可存长文本，或新增 `highlights` |
| 实用/创新/证据系数 | ❌ 无对应字段 | 需新增 |
| 星级（从系数派生） | ❌ | 前端计算 |
| "值得拆解"标记 | ❌ | 需新增 |

### 建议方案

**方案 A（轻量，推荐）：直接在 `ai_tools` 扩展字段**

```sql
ALTER TABLE ai_tools ADD COLUMN practicality_score  FLOAT DEFAULT 0;   -- 实用系数
ALTER TABLE ai_tools ADD COLUMN innovation_score     FLOAT DEFAULT 0;   -- 创新系数
ALTER TABLE ai_tools ADD COLUMN evidence_score       FLOAT DEFAULT 0;   -- 证据系数
ALTER TABLE ai_tools ADD COLUMN is_featured          BOOLEAN DEFAULT FALSE;
ALTER TABLE ai_tools ADD COLUMN highlights           TEXT;
```

- 优点：改动最小，利用现有 API 端点，加 `?featured=true` 筛选参数即可
- 缺点：评分版本历史无法追踪，不允许多轮审核

**方案 B（折中，支持多期评审）：新增独立表**

```sql
CREATE TABLE product_reviews (
    id                  SERIAL PRIMARY KEY,
    tool_id             INTEGER REFERENCES ai_tools(id),
    practicality_score  FLOAT NOT NULL,
    innovation_score    FLOAT NOT NULL,
    evidence_score      FLOAT NOT NULL,
    highlights          TEXT,
    reviewer            VARCHAR(100),
    status              VARCHAR(20) DEFAULT 'draft',
    created_at          TIMESTAMPTZ DEFAULT now(),
    updated_at          TIMESTAMPTZ DEFAULT now()
);
```

系数 → 星级映射规则：≥9.0 → ★★★★★, ≥8.0 → ★★★★☆ 等

### 实现复杂度：⭐⭐（低）

- 方案 A：约 50 行后端改动 + 1 个新前端组件（约 80 行）
- 方案 B：约 150 行后端 + 前端多一个详情页
- 预估人天：**1-2 天**

---

## 综合结论

| 功能 | 可行性 | 实施顺序 | 预估人天 | 最难点 |
|------|-------|---------|---------|--------|
| 顶部卡片 | ✅ 高 | **第 1 优先** | 1-2 天 | 时间序列基础设施从零搭建 |
| 今日值得拆解 | ✅ 高 | **第 2 优先** | 1-2 天 | 评分标准的内部一致性 |
| 赛道热力图 | ⚠️ 中等 | **第 3 优先** | 3-5 天 | 信号数据的持续采集管道 |

### 推荐实施路线

1. **先做卡片 + 拆解** — 技术风险低，2-3 天内可上线，快速建立首页的"数据感"
2. **赛道热力图先用静态/半静态数据** — 人工给 4-5 个赛道打一次分存入数据库，前端渲染热力图，验证交互和用户反馈后再上自动化评分管线
